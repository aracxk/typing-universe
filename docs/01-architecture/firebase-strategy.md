# Firebase 導入とセキュリティ戦略 (Firebase Strategy)

本ドキュメントは、「Typing Universe」における Firebase（BaaS）の活用方針、サービス選定、および悪意あるユーザーからシステムと無料枠（Sparkプラン）を守るためのセキュリティアーキテクチャを定義する。

## 1. 導入目的とサービス選定

本プロジェクトを「他者の存在を感じられるプラットフォーム」にするため、以下の機能を Firebase を用いて実装する。

1. **リアルタイム・プレゼンス（〇〇人がプレイ中）**
   - **選定サービス**: `Realtime Database (RTDB)`
   - **理由**: クライアント切断時に自動でデータを削除する `onDisconnect` が備わっており、軽量なオンライン状態の管理に最適であるため。
2. **グローバル・ランキング（スコア集計）**
   - **選定サービス**: `Firestore`
   - **理由**: スコアの降順ソートなど、複雑なクエリ処理に優れているため。

## 2. 料金保護と多層防御 (Security in Depth)

ブラウザゲームにおける「スコア改ざん」や「API連打による無料枠（書き込み/読み取り回数）の枯渇」を防ぐため、以下の4層のセキュリティアーキテクチャを必須とする。

### ① クライアント直接アクセスの禁止 (Server-Side Operations)
- **読み取り制限**: ユーザーのブラウザから直接 Firestore のランキングをクエリすることを禁止する。Next.js (App Router) 側で一括取得し、**ISR (Incremental Static Regeneration)** またはキャッシュを用いて静的に配信することで、1日数万アクセスがあっても Firestore の読み取り回数を最小限（数回〜数十回/日）に抑える。
- **書き込み制限**: Firestore の Security Rules でクライアントからの書き込みを完全ブロックする。スコア送信は必ず Next.js の API Routes (`/api/scores`) 経由で行い、`firebase-admin` を用いてサーバー側からのみ書き込みを許可する。

### ② ペイロード限界値の検証 (Domain Validation)
- APIの入り口で、Zod等を用いてペイロードを厳格に検証する。
- 例: 人間の限界（WPM > 300）を超えるタイピング速度や、ゲームの理論値を超えるスコアが送信された場合は、不正なチート通信とみなし `400 Bad Request` としてデータベースへは保存しない。

### ③ レートリミット (Rate Limiting)
- 同一IPからのスコア送信APIへのアクセスに対し、簡易的なレートリミット（例: 1分間に1回まで）を設ける。
- これにより、Botによる無限のスコア送信ループ（DoS攻撃）で Firestore の書き込み無料枠が枯渇することを防ぐ。

### ④ Firebase App Check (Bot排除)
- 正規のブラウザ環境（reCAPTCHA 等で検証）からのリクエストのみを受け付ける。
- APIキーが流出し、外部のスクリプト（curl等）からアクセスされた場合でも、App Check により Firebase レベルで通信を弾く。

## 3. 実装の前提
- 本機能は「ログイン不要（ゲスト参加）」をベースとする。
- 上記のセキュリティ基盤を整えた上で、プレゼンス機能（RTDB）とスコア送信・ランキング機能（Firestore）を順次実装していく。

## 4. インフラ管理
Firebaseのプロビジョニングは手動コンソール操作を行わず、Terraformを用いてコード化する。詳細は [インフラストラクチャ管理方針](../06-operations/infrastructure.md) を参照のこと。
