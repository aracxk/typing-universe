# UI描画戦略 (UI Rendering Strategy)

本プロジェクトでは、画面の性質に応じて最適な描画手法を使い分けます。
特にタイピングゲームの「プレイ画面（インゲーム）」においては、**HTML5 Canvas (2D)** を最適な描画手段として採用しています。

## 1. 描画手法の比較とCanvas採用の理由

ブラウザ上でゲームを構築する際の描画手法には、主に3つの選択肢があります。なぜ今回のプロジェクトでCanvasが「最適」と判断されたのか、それぞれの特徴を比較します。

### ① DOM (React / HTML / CSS)
- **特徴**: `<div>` などのHTML要素を絶対座標（absolute）で配置し、状態（State）を更新して動かす手法。
- **メリット**: テキストのレンダリングが非常に綺麗。アクセシビリティ（読み上げ等）に標準対応しており、ボタンやフォームなど一般的なUIとの親和性が高い。
- **デメリット**: 多数のオブジェクト（敵、飛び散るパーティクル、レーザーなど）が毎フレーム（1秒間に60回）動く場合、ブラウザのレイアウト再計算（Reflow）やガベージコレクションが頻発し、画面がカクつく原因になります。
- **当プロジェクトでの用途**: タイトル画面、スコアボード、設定画面など。

### ② HTML5 Canvas (2D Context) ⭐ 当プロジェクトのゲーム画面で採用
- **特徴**: 一枚の画用紙（`<canvas>`）の上に、JavaScriptの命令で直接ピクセルを毎フレーム上書きしていく手法。
- **メリット**: DOMツリーを汚さないため、**数百個のパーティクル（爆発エフェクト）や多数の敵を動かしてもパフォーマンスが低下しません**。また、ピクセル単位の操作が容易なため、レトロゲーム特有のスキャンライン（ブラウン管風）やドット絵の演出を簡単に実装できます。
- **デメリット**: テキストの自動折り返しや、クリック判定などを自前で計算する必要があります。
- **結論（採用理由）**: 今回目指す「リッチな演出を伴う2Dタイピングゲーム」において、**パフォーマンス（60FPSの維持）と実装コスト（外部ライブラリ不要）のバランスが最も優れている**ため、最適解として採用しました。

### ③ WebGL (Three.js, PixiJSなど)
- **特徴**: ブラウザのAPIを通じてGPUを直接駆動し描画する手法。
- **メリット**: 圧倒的なパフォーマンス。1万個以上のパーティクルや、高度な3D・シェーダー演出が可能。
- **デメリット**: 外部ライブラリの読み込みが必要でバンドルサイズが肥大化し、実装も非常に複雑になります。
- **結論**: 今回のレトロ風2Dゲームにおいては完全なオーバースペックであるため、見送りました。

## 2. アーキテクチャとの完璧な分離 (DDD x Canvas)

一般的に「Canvasでゲームを作る」と、描画処理とゲームのルール判定が1つのファイルに混ざったスパゲッティコードになりがちです。
本プロジェクトでは **DDD（ドメイン駆動設計）** を採用することで、この問題を解決しています。

- **ドメイン層 (`InvaderGameEngine` など)**
  - 敵の座標（x, y）やライフ、スコアの計算のみを行います。**「画面にどう描画されるか」は一切知りません。** そのため、Node.js上での高速な自動テスト（カバレッジ100%）が可能です。
- **UI層 (`InvaderCanvas.tsx` など)**
  - ドメイン層が計算した結果（座標データなど）を「読み取る」だけで、Canvas上に色やエフェクト（パーティクル）として描画することに専念します。

「ロジックは型安全なTypeScriptクラスで守り、描画は高速なCanvasに任せる」という役割分担により、保守性とパフォーマンスを両立しています。
