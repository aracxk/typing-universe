# テスト設計戦略

本プロジェクトでは、DDDのドメインルールに対する厳格な単体テストと、自律的なテスト網羅率の維持を目標とします。

---

## 1. テストの原則

1. **AAAパターン (Arrange / Act / Assert) の徹底**
   すべてのテストは準備、実行、検証の3ステップで明確に分離して記述します。

2. **境界値テスト (Boundary Value Analysis)**
   スコア計算（例：0点、最大点）、ライフの増減（例：HP 0、HP 1）など、境界となる値を必ずテストケースに含めます。

3. **外部依存の排除 (ドメイン単体テスト)**
   ビジネスロジックテストでは、UI（React等）やブラウザAPI依存を排除し、純粋な TypeScript としてミリ秒単位で実行できるようにします。

---

## 2. 時間経過（Tick）のテスト設計

ゲーム進行の中核である `deltaTime` を扱うロジックは、実際の時間に依存させるとテストが不安定になります。

- **Tickテスト手法**:
  - `vi.useFakeTimers()` を用いた時間のモック化、もしくは、純粋な関数として任意の `deltaTime` 値（例: `16.6ms`）を引数として注入し、意図通りの座標移動や状態変化（Entityの遷移）が起こるかを検証します。

---

## 3. UIとドメインの統合テスト

純粋なドメインモデル（TypeScriptクラス）とReactを接続するカスタムフック（例：`useGameLoop` や `useSyncExternalStore` のラップ）については、統合テストを実施します。

- **手法**:
  - React Testing Library を使用し、ドメインモデルの状態が更新された際に、コンポーネントが正しく再レンダリングされ、DOMまたはCanvasに反映されるかを検証します。

---

## 4. AIによるテスト実装の自動化

AIは以下の手順でテストを自律的に維持・拡張します。
- 新規ロジック実装直後、直ちに `.test.ts` を作成する。
- `vitest` を使用してテストを実行し、パスするまで自身で修正を繰り返す。
- カバレッジ不足の場合、事前の許可を求めずに自動でテストを追加して再実行する。


## 5. カバレッジ100%の強制

ドメイン層（`src/entities/**/domain/**/*.ts`）のビジネスロジックに対しては、Vitestを用いたテストで**Statement, Branch, Function, Line のすべてにおいてCoverage 100%**をシステム要件とします。不足がある場合、AIは自律的にエッジケースを分析し、テストを追加して100%を達成してからレビューへ回してください。

---

## 6. AIブラウザエージェントによるE2Eテスト・動作確認

プロジェクトには、AI（ブラウザサブエージェント）を用いてローカル環境の動作確認を行う手順がスキル（`browser-e2e-test`）としてグローバルに登録されています。

- **利用方法**: 開発中、AIに対して「ブラウザでゲーム画面のE2Eテストをして」「画面を操作してUIの挙動を確認して」などと自然言語で指示することで、AIが自律的にローカルブラウザを起動してテストを実行します。
- **検証内容**:
  - ローカルURL（`http://localhost:3000`等）へのアクセスと画面レンダリングの確認
  - キーボード操作（タイピング）やクリックなどのUIインタラクションの実行
  - 実行後のスクリーンショット・動画（WebP）を用いた視覚的エラーチェック
- **運用ルール**: チームメンバーは、UIの変更や新機能の追加時、コミット前にAIへブラウザでの動作確認を依頼し、実際の画面で問題なく動くことを確認することを推奨します。
