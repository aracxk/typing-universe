# コーディング・設計規約 (Conventions)

本ドキュメントは、`typing-universe` プロジェクト全体で一貫した設計・命名・構造を保つための規約です。
Feature-Sliced Design (FSD) に適合させた独自の構造を採用しています。

---

## 1. 命名規則

| 種類 | 規約 | 例 | 備考 |
| :--- | :--- | :--- | :--- |
| **Value Object** | PascalCase | `Score`, `TypingSpeed`, `PlayerName` | 原則イミュータブル |
| **Entity / 集約** | PascalCase | `GameSession`, `Invader` | 一意なIDとライフサイクルを持つ |
| **機能 (Feature)** | kebab-case | `invader-game`, `typing-core` | ディレクトリ名として使用 |
| **UIコンポーネント** | PascalCase | `GameCanvas`, `ScoreBoard` | Reactコンポーネント |

---

## 2. ツールチェーンとUI方針

- **静的解析・フォーマット**: `Biome` を使用します。ESLint/Prettierは禁止です。
- **コミットフック**: `Husky` + `lint-staged` を経由してコミット前に自動修正・チェックを行います。
- **ドメインテスト**: `Vitest` を用いて、ドメインロジックのミリ秒単位のテストを実行します。
- **E2Eテスト**: `Playwright` を用いて、プラットフォームのUI・画面遷移の結合テストを実行します（※Canvas内部のゲームロジック検証には使用しません）。
- **UIライブラリの禁止**: `shadcn/ui` などのライブラリは使用せず、デザインはAIが Tailwind CSS を用いて自律的に考案・実装します。

---

## 3. Feature-Sliced Design (FSD) の依存方向と境界（Bounded Context）

本プロジェクトはFSDを採用し、以下の階層（Layers）を持ちます。
さらに、複数ゲームの拡張性を担保するため、スライス内部で **ドメインごとのディレクトリ分割（Bounded Context）** を行います。

```text
[ features, entities などの内部構造 ]
├── core/       # 全ゲーム共通のドメイン・機能（例：GameSession, ActiveWord）
├── invader/    # インベーダー固有のドメイン・機能
└── standard/   # （将来用）通常タイピング固有のドメイン・機能
```

**依存の絶対ルール**:
1. **下向きの依存のみ許可**: 上のレイヤー（features）は下のレイヤー（entities）に依存できるが、逆は禁止。
2. **境界の越境禁止**: `core` は特定のゲーム（`invader`等）に依存してはならない。特定のゲームは `core` を利用・拡張することができる。
3. **ゲーム間の依存禁止**: `invader` と `standard` は互いに参照してはならない。

---

## 4. エラーハンドリング方針

- **ドメイン例外**: 不正な値（例：マイナスのスコア、空の入力）の生成は、専用のドメイン例外または `Result.err()` で早期に防ぐ（Fail-Fast）。

---

## 5. Git・コミット運用規約

コミットメッセージはすべて**日本語**で記述し、以下のプレフィックスを使用する。
（※AIは事前の許可なく自動でコミットしてはならない）

| プレフィックス | 用途 |
| :--- | :--- |
| **`feat`** | 新機能・ドメインモデルの実装 |
| **`fix`** | バグ修正 |
| **`docs`** | ドキュメントの追加・更新 |
| **`test`** | テストコードの追加・修正 |
| **`refactor`** | 振る舞いを変えないコードの改善 |
| **`chore`** | 環境設定、ビルド構成の変更 |

---

## 6. ドキュメントとコードの同期検証

- 定数やビジネスルールを変更した際は、インラインコメント、単体テスト、仕様書すべてで不整合がゼロであることを確認する。
- 意味のある設計決定を行った際は、ADR (Architecture Decision Record) として残す。

## 7. JSDoc記述規約（AI駆動開発時代のアプローチ）

本プロジェクトでは、「TypeScriptの型をただ復唱する冗長なコメント」を廃止し、**「AIや開発者が誤認しやすい単位・境界制約・設計意図」に特化したJSDoc**を必須とします。

### 対象スコープ（記述必須）
1. **ドメイン層 (`src/entities/`)**:
   - すべての Class, Interface, Type
   - すべての `public` メソッド、静的ファクトリメソッド（`create`等）
2. **公開API・境界インターフェース (`features/`, `shared/`)**:
   - リポジトリ、ゲームストア、Custom Hooksの公開関数・返り値

### やるべきこと (Do)
- **単位の明記**: 時間は `ms`（ミリ秒）か `sec`（秒）か、速度は `px/sec` かなどを必ず明記する。
- **境界制約の明記**: `0以上の数値`、`空文字不可`、`負数はエラー` などのバリデーション条件を記述する。
- **Result型の仕様**: `Result.err` が返る具体的な条件（エラーコードや理由）を記述する。
- **タグの活用**: `@param 引数名 説明`（型名はTSと重複するため省略）、`@returns 戻り値の説明` を記載する。

### やってはいけないこと (Don't)
- **変更履歴・改修コメントの直書き禁止**: `// 修正:` や `// 〜から〜へ変更` などの経緯・差分理由は Git コミットメッセージとPRで表現すべきであり、コード内に残してはならない。
- **実装の復唱・長文解説の禁止**: コードを読めば自明な処理の流れを日本語で長々と復唱するインラインコメントはノイズとなるため禁止。
- **AI特有の言い訳・自己主張コメントの禁止**: `// ここでエラーハンドリングを追加して安全性を高めています` などの不要な主張コメントは書かない。
- **TypeScriptと重複する型名の再記述**:（例: `@param {number} x` は不要）。
- **自明すぎる説明**:（例: `/** スコアを取得する */ get score()` は不要）。
- **絵文字の使用**:（コード・コメント・コミット・ドキュメントすべてで完全禁止）。

## 8. AI自動生成UI（StitchMCP等）の組み込みルール

AIエージェント（StitchMCP等）によって生成されたHTML/Reactコードをプロジェクトに組み込む際は、以下の事項を必ず遵守・精査すること。「見栄えが良いから」という理由だけで無批判に流し込むことを固く禁ずる。

1. **完全な日本語化**: 
   - 英語のダミーテキスト（"LOREM IPSUM", "PLAY NOW" 等）やプレースホルダーはそのまま使用せず、プロジェクト要件に適合する自然で分かりやすい日本語に必ず書き換えること。
2. **不要な要素（ハリボテ）の排除**: 
   - 現在のドメイン実装において機能しないボタン（「設定」「開始」等）、意味のないバッジ（「〇〇人がプレイ中」「ウェーブ制限」など）は絶対に削除するか、実働する形に置き換えること。
3. **要件との照らし合わせ（過不足の精査）**: 
   - プロジェクトの要求仕様と照らし合わせ、「本当にこの要素は必要か」を常に問い、過剰な装飾要素は削ぎ落としてミニマルで本質的なUIを保つこと。
