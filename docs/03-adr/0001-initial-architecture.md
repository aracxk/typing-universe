# ADR 0001: プロジェクト初期のアーキテクチャおよび技術スタック選定

- **日付**: 2026-09-14
- **ステータス**: 承認済

## コンテキスト（背景と課題）
タイピングゲーム「Typing Universe」を立ち上げるにあたり、以下の要件を満たす基盤が必要となった。
1. **複数ゲームの共存**: インベーダー形式など、複数の異なるゲーム性が同一プロジェクト内で共存・切り替え可能であること。
2. **インフラのシンプルさ**: Vercelへのデプロイのみとし、Supabase等の外部DBやログイン機能は持たないこと。ただしSEO対策は行う。
3. **前例（ai-note-market）の知見**: DDD（ドメイン駆動設計）、ゆびきたす言語、厳格なテストという思想は引き継ぐ。

## 決定事項（Decision）
以下のアーキテクチャと技術スタックを採用する。

1. **アーキテクチャ**: Feature-Sliced Design (FSD)
2. **フレームワーク**: Next.js (App Router)
3. **状態管理**: DBを使用しないため、ゲームステートはすべてクライアント（Reactの状態管理、または Zustand等）で完結させる。

## 理由（Why / トレードオフ）

### 1. なぜ Clean Architecture ではなく Feature-Sliced Design なのか？
- 複数のタイピングゲームが共存する場合、ゲームごとに必要なUI、ロジック、ドメインルールが異なる。
- Clean Architectureの横割り（レイヤーごとの分割）では、新しいゲームを追加する際に複数のディレクトリ（Presentation, UseCase, Domain, Infrastructure）をまたいでファイルを追加する必要があり、ゲーム間の結合度が高まりやすい。
- FSD（縦割り）であれば、`features/invader-game` のように機能単位でスライスできるため、各ゲームの独立性が保たれ、新しいゲームの追加や削除が容易になる。

### 2. なぜ DB（Supabase等）を使わないのか？
- ユーザーからの「まずは作ってVercelでデプロイするだけ」「ログイン機能なし」という強い要件を最優先したため。
- ハイスコアの保存等の永続化が必要になった場合は、ブラウザの `localStorage` を利用する方向で妥協（トレードオフ）する。

### 3. なぜ Next.js なのか？
- 「SEO対策をする」という要件に対し、SSG（Static Site Generation）やメタタグ管理を強力にサポートしているため。
- Vercelとの親和性が最も高く、ゼロコンフィグでデプロイが完了するため。
