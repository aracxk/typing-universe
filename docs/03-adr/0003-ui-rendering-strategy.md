# ADR 0003: UI描画戦略（Canvas 2Dの採用）

- **日付**: 2026-09-15
- **ステータス**: 承認済

## コンテキスト（背景と課題）
インベーダー型タイピングゲームの実装にあたり、「大量のパーティクル（爆発エフェクト）」や「60FPSでの滑らかなテキスト移動」といったリッチな演出が求められた。
ブラウザ上での描画手法としては、主に「DOM (React/HTML/CSS)」「HTML5 Canvas (2D)」「WebGL (PixiJS等)」の3つの選択肢が存在したが、今後の拡張性やパフォーマンス、実装コストの観点から最適な手法を決定する必要があった。

## 決定事項（Decision）
ゲームプレイ画面（インゲーム）の描画において、**HTML5 Canvas (2D)** を採用する。
ロジック（DDD）と描画を完全に分離し、Canvasは「計算結果を毎フレーム読み取って描画するだけ」の責務を持たせる。

## 理由（Why / トレードオフ）

### 1. DOMの限界
DOMは文字のレンダリングやアクセシビリティには優れるが、数十〜数百の要素（敵やパーティクル）を60FPSで動かすとブラウザのレイアウト計算（Reflow）がパンクし、カクつき（パフォーマンス低下）の原因となるため見送った。

### 2. WebGL (PixiJS/Three.js) のオーバースペック
WebGLを利用すれば1万個以上のパーティクルや強力な発光（Bloom）エフェクトが可能になるが、外部ライブラリへの依存（バンドルサイズの肥大化）やReactとの連携コストが生じる。
今回は「ゲーム性」を重視しており、過剰な演出は現状のビジョンにおいて不要（オーバースペック）であると判断した。

### 3. Canvas 2D が最適解である理由
外部ライブラリなし（実装コスト低）で、数百個のパーティクルやレトロなスキャンラインエフェクトを60FPSで処理できる。
現在の「タイピング × 面白さ」を追求するフェーズにおいて、パフォーマンスと保守性のバランスが最も優れている。

## 影響（Consequences）
- **メリット**: 
  - DDDで構築された `InvaderGameEngine` に一切変更を加えることなく、描画のみをCanvasへ切り替える（FSDの恩恵）ことができた。
  - スマホからPCまで、幅広い端末でサクサク動作する軽量なゲーム基盤が完成した。
- **デメリット**:
  - 今後万が一「数万個のパーティクル」「3D空間」といった超リッチな演出が必要になった場合は、Canvas 2DからWebGLへ再度リプレイスする必要がある。（ただし、ドメイン層は分離されているため移行コストは描画層のみに留まる）
