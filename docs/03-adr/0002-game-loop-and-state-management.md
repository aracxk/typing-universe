# ADR 0002: ゲームループと状態管理の設計手法

- **日付**: 2026-09-14
- **ステータス**: 承認済

## コンテキスト（背景と課題）
`ai-note-market` ではCRUD中心の設計であったが、今回のインベーダー形式タイピングゲームでは、以下の要件が発生する。
1. **時間経過による状態変化**: ユーザーが操作しなくても敵（インベーダー）が常に移動する。
2. **高頻度な更新**: 60FPS（1秒間に60回）の座標更新が必要。
3. **キーボードのリアルタイム判定**: キー入力と画面上の敵の状態を即座に突き合わせる必要がある。

React標準の `useState` とコンテキストを用いた状態管理では、毎フレームの更新によりコンポーネントツリー全体が再レンダリングされ、パフォーマンスが著しく低下する。

## 決定事項（Decision）

1. **DDDモデルの非React化（純粋TSによる管理）**:
   ゲームのコア状態（インベーダーの座標配列、ライフ、スコア）は、ReactのStateではなく、純粋なTypeScriptクラス（Entity/Aggregate）インスタンス内に保持する。
2. **メインループ（Tick）の導入**:
   `requestAnimationFrame` を用いたメインループ関数を設け、毎フレームごとに Entity の `update(deltaTime)` を呼び出して状態を計算する。
3. **描画（UI）への同期手法**:
   高頻度で更新される座標情報などの描画は、以下のいずれかの手法を取る。
   - **Canvas API の利用**: ReactのDOMに依存せず、`<canvas>` 上に直接描画する（DOMの再レンダリングを回避）。
   - **Zustand等のサブスクライブ機能の利用**: DOM（HTML/CSS）で描画する場合は、必要なコンポーネントだけがピンポイントで再レンダリングされるよう軽量なストアを使用する。

## 理由（Why / トレードオフ）

- **Canvas API vs DOM**:
  インベーダー形式のように「多数の要素が同時に動く」場合は、DOM要素を毎フレーム動かすよりも Canvas の方がパフォーマンス的に有利で、ゲームらしい表現（パーティクルなど）も実装しやすい。よって、ゲームボード領域はCanvasベース、HUD（スコア等の固定UI）はDOMベースというハイブリッド手法を基本方針とする。
- **純粋なTSへの分離**:
  ロジックをReact Hooksの中に閉じ込めると、Vitestを用いた「ドメイン単体テスト」が難しくなる（React Testing Libraryが必要になる）。ゲームの「当たり判定」や「スコア計算」は完全にUIから切り離すことで、AAAパターンでの高速なテストが可能になる。
