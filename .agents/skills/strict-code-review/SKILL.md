# 厳格コードレビュー・プロトコル (Strict Code Review Protocol)

本スキルは、Typing Universe におけるコード品質、FSDアーキテクチャ規約、ゲームロジックの純粋性を担保するための標準コードレビュー・実行エンジンです。
誰が実行しても常に同じ判定基準・チェック項目・出力フォーマットで客観的なレビューを実施します。

---

## 1. レビュー実行手順 (Execution Steps)

レビュー依頼を受けたエージェントは、以下の手順を順番に実行すること。

1. **静的検証・テストの実行**:
   - `npm run typecheck` を実行し、型エラーが 0 件であることを確認する。
   - `npm run test` を実行し、全単体テストが All Green であることを確認する。
   - `npx @biomejs/biome check` を実行し、Error, Warn, Info などの警告が一切出力されない状態であることを確認する。
2. **差分・対象コードの精査**:
   - `git diff`（または対象ファイル群）を確認し、変更内容を特定する。
3. **チェックリストによる全件照合**:
   - 以下の「2. レビュー観点チェックリスト」の全項目を照合し、合否を判定する。
4. **標準レビューレポートのチャット表示**:
   - 以下の「3. 標準レビューレポート出力フォーマット」に従い、メインAIに対してレビュー結果を返答する。

---

## 2. レビュー観点チェックリスト (18 Items)

### カテゴリA: FSDの依存ルールと境界
- [ ] **A-1: 下向き依存の徹底**: `features` 層が `entities` 層に依存しており、逆方向の依存が存在しないか？
- [ ] **A-2: クロスドメインの禁止**: `invader` ドメインが `standard` に依存するなど、同階層の横の依存が発生していないか？（`core` のみ全ドメインから参照可能）

### カテゴリB: ゲームループとReactの分離
- [ ] **B-1: ドメイン層の純粋性**: `entities` 内のクラス（ゲーム状態、Tickなど）に React (`useState`, `useEffect`) などのUIライブラリがインポートされていないか？
- [ ] **B-2: 高頻度更新の最適化**: 60FPSでの状態更新を伴う処理において、無駄なReactの再レンダリングを誘発しない設計（`useSyncExternalStore`, Canvas, useRef 等）になっているか？

### カテゴリC: エラー設計と型安全
- [ ] **C-1: ドメイン例外と早期リターン**: 不正な値（例：マイナスのスコア等）の生成をコンストラクタやファクトリメソッドで確実に防いでいるか？
- [ ] **C-2: 値の不変性（Immutable）**: エンティティや値オブジェクトのプロパティが `readonly` で保護され、安易な Setter が存在しないか？

### カテゴリD: 単体テストの網羅性と品質 (Tickテスト)
- [ ] **D-1: AAA パターンの徹底**: テストコードが Arrange（準備）/ Act（実行）/ Assert（検証）の構造で記述されているか？
- [ ] **D-2: 時間経過（Tick）テスト**: `deltaTime` を注入することで、実際の時間経過に依存せず、境界値のテストが網羅されているか？
- [ ] **D-3: 揺らぎ吸収のテスト**: `ActiveWord` のようなローマ字入力の揺らぎ吸収ロジックに対する網羅的な入出力テストが存在するか？

### カテゴリE: ドキュメント・規約・ADR同期
- [ ] **E-1: 絵文字の不使用**: ソースコード、コメント、ドキュメント、コミットメッセージに絵文字が一切含まれていないか？
- [ ] **E-2: ユビキタス言語の完全一致**: コード上の変数名・クラス名が `docs/notebooklm/` 内の用語（`GameSession`, `ActiveWord` 等）と完全に一致しているか？
- [ ] **E-3: ADR の起票と記録**: 新しい設計方針や重大なルールの追加が行われた場合、`docs/03-adr/` に記録されているか？
- [ ] **E-4: Lint警告のゼロ化**: Biomeからの提案が残っていないか？（波線がある場合は、コードを修正するか `biome.json` でオフにするかを提案すること）
- [ ] **E-5: JSDocの標準化**: ドメイン層（entities）や公開APIにおいて、単位（ms, px/sec）や境界条件、Result型の失敗条件がJSDocとして適切に明記されているか？型名のみの冗長な記述や自明すぎる記述になっていないか？
- [ ] **E-6: 変更履歴・無駄なコメントの排除**: `// 修正:` や `// 〜のため変更` などの変更履歴・改修理由コメント、またはコードの動作を復唱するだけの無駄な長文コメントが混入していないか？（変更履歴はGitコミットとPRで表現する）

### カテゴリF: フロントエンドUI設計とファイル分割
- [ ] **F-1: コンポーネントライブラリの不使用**: `shadcn/ui` や MUI 等の外部UIフレームワークがインストール・使用されていないか？
- [ ] **F-2: AI主導のTailwindデザイン**: AI自身が Tailwind CSS のクラスを直接記述し、ゲームの世界観に合ったUIを自律的にデザインしているか？
- [ ] **F-3: Hooksの絶対分離とファイル分割**: `.tsx` ファイル内に `useState` や `useEffect` などのロジックが直書きされておらず、カスタムフック (`useXxx.ts`) に分離されているか？また、1つのファイルが肥大化せず適切なコンポーネント単位で分割されているか？
- [ ] **F-4: AI生成UIの無批判な取り込み防止**: StitchMCP 等で生成されたUIに対し、英語のダミーテキストが日本語化され、機能しない「ハリボテ」のボタンやバッジが確実に削除（または実働化）されているか？

## 3. 標準レビューレポート出力フォーマット

```markdown
# 厳格コードレビュー結果 (Strict Code Review Report)

- **対象差分**: `...`
- **型チェック (tsc)**: 合格 (エラー 0 件) / 不合格
- **単体テスト (Vitest)**: 合格 (xx 件 All Green) / 不合格
- **総合判定**: 【承認 (Approve)】または【要修正 (Changes Requested)】

---

## 1. チェックリスト合否サマリー

| カテゴリ | 合格項目数 | 状態 |
| :--- | :--- | :--- |
| A: FSDの依存ルール | 2 / 2 | 合格 |
| B: ゲームループの分離 | 2 / 2 | 合格 |
| C: エラー設計・型安全 | 2 / 2 | 合格 |
| D: 単体テスト・Tick | 3 / 3 | 合格 |
| E: ドキュメント・規約 | 6 / 6 | 合格 |
| F: フロントエンド設計 | 4 / 4 | 合格 |

---

## 2. 指摘事項（重大度別）
- **[Critical]** (マージをブロックする重大なバグ・設計破綻) ➔ なし
- **[Warning]** (修正が推奨されるルール違反・エッジケース漏れ) ➔ なし
- **[Suggestion]** (将来の保守性向上のための提案) ➔ ...

```
